# lahqr sweep updates and the small-n real Schur gap (#285)

## Decisions
- The issue assumes OpenBLAS runs multishift+AED below n = 75 and colmat does not. It does not: reference `dhseqr` only
  sends n > NMIN = 75 to `dlaqr0`, and a callgrind run of OpenBLAS 0.3.26 `dhseqr` at n = 64 spends 60% of its instructions in
  `dlahqr_`. Both libraries run the same double-shift Francis kernel there, so the gap is the efficiency of colmat's `lahqr`,
  not the selection threshold. Raising or lowering `blocking_threshold` is therefore not the lever (the contributor measured
  no change either).
- Stage answer: the QR iteration kernel. The ratio is flat in n (1.48 -> 1.60 from n = 16 to 64), which rules out a fixed
  per-call cost (allocation/dispatch); Hessenberg is outside the measured region and already at parity in the issue; the
  deflation scan is O(window) per iteration against O(n * window) per sweep.
- Change: the three reflector applications of the bulge sweep (rows, columns, `Z`) use a zipped traversal with the original
  operation order instead of indexed loops with a bounds assert per element. No rounding changes. Only `lahqr`;
  `multishift_qr_sweep` and `complex_schur.rs` keep indexed loops.
- Not done, deliberately: a scalar 3-vector Householder in place of `make_householder_in_place` (about 13% of instructions
  incl. `norm_l2`). It would have to reproduce `norm_l2`'s architecture-dependent SIMD pairwise summation bit for bit; a
  different rounding is a proposal for the maintainer, not part of a performance fix.

## Verification conclusions and constraints
- Bit-identical on 28 cases (hash of T, Z, wr, wi); a committed test covers reconstruction, orthogonality and values-only vs
  full-Schur eigenvalue bit equality (`lahqr_sweep_updates_and_values_only_mode`; it fails when `t3` is replaced by `t2`).
- Gain is small: n = 64 values-only colmat 944.6 / 942.5 / 944.8 us before, 899.2 / 896.3 / 895.4 us after (-5%, runs separate
  cleanly), instructions -9%. The OpenBLAS reference moved more than the gain (589-590 us in five runs, 683 us in one), so no
  gap ratio is claimed beyond about 1.5x before and after.
  The issue's 2.1-2.5x did not reproduce here (1.5-1.6x), on a different CPU and OpenBLAS build.
- One pinned core, boost on (no root to change it), 3 runs x 301 calls per side. Not an acceptance-grid run. No upstream faer revision
  was measured: the change is to fork code that upstream also has, and no upstream comparison was made.
- Probe source and raw runs: `evidence/2026-11-27-lahqr-sweep-285.tar.gz`.
