# `lu` / `solve` on evo2 against MKL: the recorded loss is the owning route's factor allocation, not the factorization

Issue: [tensor4all/faer#123](https://github.com/tensor4all/faer/issues/123) (folded into umbrella
[tensor4all/faer#168](https://github.com/tensor4all/faer/issues/168)), ranked as the largest
remaining `lu`/`solve` loss by [tensor4all/faer#404](https://github.com/tensor4all/faer/pull/404).

Measured revision: `c820e447` (`t4a-faer` 0.32.0, `origin/main`) for the fork arm and
`faer-v0.24.4` (`0539947f`) for the upstream control row, both in one `fbench` binary
(`tensor4all/faer-benchmark` `3b80b90`), MKL **2026.2** (`/opt/intel/oneapi/mkl/2026.2`,
`libmkl_rt.so.3`, Intel OpenMP `iomp5`). One host, one session: **EVO-X2**, AMD Ryzen AI MAX+ 395
(Zen 5), 32 logical / 16 cores, SMT on (sibling `n + 16`), two 64-MiB L3 domains (CPUs 0-7/16-23
and 8-15/24-31), `performance` governor, **boost on** (turning it off needs a password this
session does not have), no `x86-v4`/`nightly`. MKL is the only BLAS: OpenBLAS is not installed
here. Nothing in this record is comparable with the MKL figures of the 2026-11-11/12 records: those
came from other hosts.

**Purpose of the run**: diagnosis / merge decision on `c820e447` (`main`, not a released pin), so
none of these numbers is a publication run and none of them may enter the published site
(`R-performance-95` in shinaoka's profile). **Yardstick**: MKL, because that is what the ranking
and this increment were defined against and OpenBLAS is not installed here; MKL is read through
its public API only, and the finding does not depend on it - it is faer's own owning route against
faer's own in-place route (`R-performance-90` prefers OpenBLAS for cause analysis).

Every number below is recomputed by
[`evidence/2026-11-12-lu-mkl-evo2/aggregate_lu123.py`](evidence/2026-11-12-lu-mkl-evo2/aggregate_lu123.py)
(campaign cells, tables A and B),
[`aggregate_probe.py`](evidence/2026-11-12-lu-mkl-evo2/aggregate_probe.py) (phase decomposition,
tables C and E) and
[`aggregate_alloc.py`](evidence/2026-11-12-lu-mkl-evo2/aggregate_alloc.py) (table D) from the raw
CSVs in that directory. `aggregate_lu123.py` prints how many processes it kept per cell and
`aggregate_alloc.py` how many rows it kept per run; none of them assumes a count.

## Decisions

- **The ranking's cell is the owning route, and that is what reproduces here: 2.14x at f64 and
  1.69x at c64, `lu`, n = 512, 8T** (tables A and B, `owning / MKL`). The same cell timed through
  the `in_place` route is **0.95x and 0.82x**, and `solve` is the same shape (owning 1.18/1.04x,
  `in_place` 0.95/0.89x). Over the whole grid (n = 128..1024, both orders, 1T/4T/8T, f64/c64)
  the median ratio is **0.90x for the owning route and 0.58x for the in-place one** (0.895 and
  0.583 over the 96 cells each), the in-place route never exceeds 1.18x anywhere, and the owning
  route is above 1.2x in 30 cells - all of them at 4T or 8T and n >= 256, in both families, worst
  in the 8T `lu` cells at 2.1-2.5x. Those are the cells where the second factor stops fitting the
  heap. `fbench` has timed both routes since #49 (`fbench` `7bb8105`, "one
  in_place body for both faer rows; allocation outside the clock"), so the ranking's `lu`/`solve`
  rows - and the page the 2.8x was read from, `71b25ffb7ae3`, which predates that body - are the
  owning route only.
- **The factorization itself is at or ahead of MKL at this cell and at every thread count**
  (table C, `factor_only`): 0.637 f64 and 1.566 c64 at n = 512, 8T, on a prepared column-major
  buffer, against MKL's `?getrf` 0.739 / 2.081 in the same binary. There is no panel, kernel or
  triangular-solve stage behind MKL here, so no amount of work inside the factorization can move
  the published ratio below about 1.0x while the owning route allocates two dense factors.
- **What the owning route adds is one dense second factor's allocation, and it is memory, not
  copy** (table C). `owning - owning_no_split` = 0.822 f64 / 1.668 c64 at 8T, and that difference
  is the buffer `split_LU` allocates for `U`: `clone_only` (the factor buffer) 0.056 and
  `alloc_zeros` (`U` alone) 0.032 both cost nothing while they are the only large buffer alive,
  while holding both - which is exactly what `split_LU` does
  (`faer/src/linalg/solvers.rs:1161`) - is 0.827 with **992 minor page faults per call**, i.e.
  `2 n^2` 8-byte elements = 4 MiB of freshly provisioned pages. The triangular copies the phase
  actually performs are 0.027 (upper copy) + 0.016 (strict-lower zero) = 5% of it. The cost is
  thread-independent (0.833 / 0.820 / 0.822 at 1T/4T/8T; 1.724 / 1.691 / 1.668 for c64) and scales
  with bytes, not flops (table E: 0 / 224 / 992 / 4064 faults at n = 128 / 256 / 512 / 1024 =
  0.2 / 1.0 / 4.0 / 16.0 MiB).
- **Rewriting the split is not the lever; three rewrites were measured** (table C). One
  contiguous span per column (`split_colslices`) is 0.877 and the same rewrite through `MatIndex`
  (`split_colwise`) 0.888, against the current `split_upper_only`/`split_zero_only` 0.865/0.855 -
  inside the noise of the phase they would replace; row-wise copies (`split_rowwise`) are 3.8,
  because a row is not contiguous in a column-major buffer; and a hand-spawned 8-thread split
  (`split_std_threads`, diagnostic only, the library must use its own team) is 1.010, i.e.
  *slower*, because the fault cost does not parallelise. Every variant pays the same 992 faults,
  and so does taking `U`'s buffer before the factor buffer instead of after (`owning_u_first`
  1.526 against `owning` 1.545, `alloc_then_clone` 0.821 against `clone_and_alloc_only` 0.827):
  the order of the two allocations is not what costs.
- **The term is the allocator's growth policy, not faer** (table D). Same binary, same cells, one
  environment variable: with `MALLOC_TOP_PAD_=33554432` the owning `lu` goes 1.572 -> 0.813 (f64)
  and 3.523 -> 1.981 (c64), `owning - in_place` falls to 0.164 / 0.320, and MKL does not move
  (0.739 -> 0.697, 2.085 -> 2.045). `MALLOC_MMAP_THRESHOLD_=64 MiB` removes about half of the
  penalty (1.221 / 2.807) and `MALLOC_TRIM_THRESHOLD_=64 MiB` none of it (1.607 / 3.585); the
  surviving 0.164 / 0.320 is what an `n^2` copy plus a fresh pointer costs, and the byte-identical
  upstream `split_LU` pays 0.225 / 0.188 of it under the same padding in its own process. Under
  that padding the owning route is **1.17x MKL at f64 and 0.97x at c64** (`solve` 1.16x / 1.00x).
  So what the ranking charges faer for is glibc growing the heap for a 2-MiB chunk under its default
  128-KiB `M_TOP_PAD` and the kernel zeroing what it hands out; a library cannot remove that without
  keeping an arena of its own. *Hypothesis, not measured*: the reason `M_TRIM_THRESHOLD_` does
  nothing while `M_TOP_PAD_` removes the whole term is that the pages are lost on the way *in*
  (each growth asks the kernel for exactly what was requested, so the next call's chunk is never a
  recycled one), not on the way out; the record has no trace of glibc's internal decisions, only
  the four cells above.
- **The penalty is not even stable across rows of the same binary**: `solve`, which factors and
  then solves, pays only 0.15 (f64) / 0.29 (c64) for the same split at the same n and T, against
  `lu`'s 0.88 / 1.80 (tables A and B, `owning - in_place`). Same code, same sizes. The
  explanation this record *proposes* - that whether the second 2-MiB chunk comes from the heap or
  from a fresh mapping depends on what the process allocated before it - is **a hypothesis, not a
  measurement**: it is consistent with the `MALLOC_*` cells and with the upstream control row,
  whose split costs only 0.06-0.10 / 0.18-0.20 unpadded in its own process while its `split_LU` is
  byte-identical (`extern/upstream-faer/faer/src/linalg/solvers.rs:955`), and the upstream arm's
  factorization
  allocating a bigger scratch buffer first would fit it, but nothing here traces glibc. The
  one-row-per-process run (`alloc/alloc.csv`, the `row-isolated-*` runs, `lu` only) rules out the
  *cross-arm* version of the story - each arm's gap survives measuring it alone - and leaves the
  history-dependence itself unproven.
- **#123's scaling premise does not carry this cell either.** From 1T to 8T the owning route goes
  2.478 -> 1.545 (1.60x, table C) while the factorization alone goes 1.597 -> 0.637 (2.51x): most
  of the serial share an Amdahl reading attributes to the panels is the split's allocation, plus
  the copy into the factor buffer (`clone_only` 0.057 column-major; for the row-major input no phase
  copies the input, so the record takes it as the derived difference `owning_no_split - factor_only`
  in the c-order cell, 0.369 against 0.090 in the f-order one - which is why the c-order gaps in
  tables A and B are the larger ones). Whether the panels themselves serialise cannot be decided on
  this host - see below.

## What this record does not do

No library change, no version bump, no API change: the measurement contradicts the premise the
next stage would have been chosen from - no LU stage is behind MKL at these cells, and the owning
route's loss is a fresh-page provisioning of one dense factor - so this is the record and the
decision points, not the change.

The measured next stages, in the order the numbers rank them:

1. **How the ranking times `lu`/`solve`** (`tensor4all/faer-benchmark`; #404). The `lu`/`solve`
   rows rank the owning route, whose cost at n >= 512 is dominated by allocating two dense factors
   per call - 0.8 ms of 1.6 at f64 n = 512, 1.7 of 3.5 at c64, and 3.9 of 6.8 / 9.6 of 17.7 at
   n = 1024 (f-order; 5.6 / 12.1 in c-order) - while MKL's `?getrf` allocates nothing. The
   `in_place` rows that would make it like-for-like have existed since #49 and are at 0.82-0.97x at
   n = 512, 8T (0.40-0.97x over all thread counts at that size, 0.37-1.18x over the whole grid).
   Ranking the pair, or reporting the in-place row as the factorization figure, is a harness/record
   decision; nothing in the library needs to change for it.
2. **`PartialPivLu`'s storage** (`faer/src/linalg/solvers.rs:1161`, `:1190`). The owning route
   allocates `2 n^2` per call and `L()`/`U()` are why. Removing it - views into the packed factor,
   lazy materialization, or a caller-provided buffer - changes what those public methods return,
   so it is a design decision; this record only prices it, by the two quantities it measured at
   f64 n = 512 8T in the `lu` row: `owning - owning_no_split` 0.822 of the 1.545 (table C) and
   `owning - in_place` 0.878 of the 1.580 (table A) - and only 0.153 of 0.804 in the `solve` row,
   per the instability above. Note that the caller-provided route already exists and is the one the
   campaign times as `in_place`: `lu_in_place` on a caller's buffer needs neither of the two
   allocations, which is
   why it is at 0.95x at n = 512, 8T in that family. The owning route is the one that pays.
3. **The panel serialization #123 was opened for**: not measurable on this host. 8T is the largest
   cell that stays inside one L3 domain (CPUs 0-7 share `index3/shared_cpu_list`), and the factor
   gains a clean 2.51x from 1T to 8T with no 4T anomaly (table C), so nothing here supports or
   refutes it. It needs the 64-core host and the #168 decision cell.

## Verification conclusions and constraints

- **Both faer arms and MKL run in one binary, one process per cell**, with the rows interleaved
  inside each cell by `--rotate-rows 3`, so no arm owns a warm-up or a cool-down; 3 processes per
  cell (tables A and B) or 5 repetitions inside one process after a 250 ms prime (tables C-E).
  The ratios are between medians.
- **CPU sets follow this host's own record** (`docs/worklogs/2026-11-12-eigh-vs-mkl-evo2.md`): 1T =
  CPU 0, 4T = 0-3, 8T = 0-7, i.e. one L3 domain, and the reporting process plus its idle gate run
  on CPUs 8-15/24-31, outside the measured domain. The campaign's `zen5-cpu` profile describes a
  24-logical/12-core machine and its `record_run.py` refuses this host, so these numbers are filed
  under this record, not under a profile name.
- **Idle gate**: `benchmarks/scripts/pinned.sh` of the harness - 3 s window, 5% busy, 3 retries,
  verdict recorded per process, and for the `fbench` cells copied into the CSV as `#` lines. All 36
  cell processes and all 48 probe cells were accepted on attempt 1; no other measurement ran on the
  host during these runs.
- **MKL's thread count is read back per cell** (`vendor_threads` = 8 in every kept row), and
  `RAYON_*`/`OMP_*`/`MKL_*`/`GOMP_*` are stripped from the child's environment; only
  `OMP_NUM_THREADS` is set by the harness.
- **Boost stays on**, so nothing in this record is a boost-off baseline: the ratios are
  same-condition, and every arm of a cell runs in the same process.
- **Correctness**: every campaign cell is checked before it is timed (`Op::check` reconstructs the
  input from the returned factorization and rejects a replacement result), so a wrong answer
  cannot have been recorded as a fast one. The probe's phases are timings only - they are readings
  of code paths that write the same values as `split_LU`, not independent implementations on
  trial.
- **The probe is not the library, in two places that matter for reading table C**: it hoists the
  permutation vectors out of the loop while `new_imp` allocates two `m`-element `Vec`s per call
  (`solvers.rs:1200-1203`, 8 KiB at n = 512), so the campaign row contains those and
  `owning - owning_no_split` does not; and `owning_u_first` is a hand copy of `new_imp` + the
  split, which is what makes it the measured answer to "would allocating `U` first help".
- **The allocator rows (table D) are diagnostics, not cell measurements**: they set `MALLOC_*`
  explicitly and exist only to attribute table C's fault count. No number in tables A-C depends on
  them.
