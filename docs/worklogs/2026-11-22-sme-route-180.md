# Does colmat's `matmul` reach the t4a-gemm SME kernel? (2026-11-22, #180 unit 1)

Question from the review of #180: `upstream-reports/performance/perf-gemm-001-apple-sme-unused`
shows upstream `gemm` 0.19.0 never selecting a matrix-unit kernel on M4/M5. Does colmat, which
depends on the `t4a-gemm` fork, actually run the SME kernel for `f32`/`c32`/`c64` (and `f64`) at
the sizes that `t4a-gemm-common` 0.20.4 `sme_thresholds.rs` routes to SME?

## Decisions

- **Answer: yes.** The kernel is reachable for all four types. At one thread the kernel each call
  reaches is exactly the one the `sme_thresholds` gate picks, on every shape probed.
- No dispatch change is needed, so none is made. What lands is the probe (an example plus an
  lldb hit-count script), so the question can be asked again after a `t4a-gemm` bump.

## Host

Apple M5 Max, macOS 26.7.2, rustc 1.96.0. Measured on the library code of `c82d2b8f`. The PR is rebased on `318e775b`, which adds only the QL/RQ modules (`faer/src/linalg/{ql,rq}`, plus two lines in `linalg/mod.rs`) and nothing on the `matmul` path. `hw.optional.arm.FEAT_SME = 1`,
`FEAT_SME_F64F64 = 1`, `SME_F32F32 = 1` (this release has no `FEAT_`-prefixed spelling of the
F32F32 flag; the probe in `gemm-common/src/cache.rs` accepts both spellings), `sme_max_svl_b = 64`.
The host was shared with other work (load average 3.6 to 7.3 on 18 cores), with no pinning; macOS
has no thread affinity. Raw files are in `evidence/2026-11-22-sme-route-180/`.

## Static route

1. `faer/Cargo.toml`: the `std` feature turns on `gemm/apple-sme`, and the default features
   include `std`.
2. `linalg::matmul::matmul_imp` (`faer/src/linalg/matmul/mod.rs`), native `f32`/`f64`/`c32`/`c64`:
   - `m * n * k <= 16^3` goes to `nano_gemm`, which is far below every SME gate (the smallest is
     `m*n*k >= 131072`);
   - `Par::Team` goes to `utils::team::gemm_team`. Off x86_64 that is `gemm_tiled`: when
     `tile_split` picks a grid, one sequential `gemm::gemm` call per member, each on its own tile
     of the output; when it declines (`GEMM_BELOW_FLOOR`), the whole product as one sequential
     call on the calling thread;
   - otherwise one `gemm::gemm(.., Parallelism::None)` call.
3. `t4a-gemm` 0.20.1 `gemm_dispatch` calls `get_gemm_fn()` for the element type. On aarch64 Apple
   with `apple-sme`, `init_gemm_fn` returns `sme_gate::gemm_basic` when `HasAppleSme::get()`
   (f64/c64) or `::get_f32()` (f32/c32) holds. That function sends each call to `sme::gemm_basic`
   when `SmeThresholds::wants_sme(m, n, k)` holds, and to `neon`/`neonfcma` otherwise.

The gate sees the shape of each sequential call. On a team that cuts the product, that shape is a
tile, not the whole product.

## Dynamic route: `scripts/sme-route-probe.sh`

The script runs `faer/examples/sme_route.rs` (the public `matmul` entry, `Par::Seq` or a held
team) under lldb, and counts breakpoint hits on `<crate>::gemm::<mod>::sme::gemm_basic` and on the
NEON fallback (`neon` for f32/f64, `neonfcma` for c32/c64). It covers the crossover shapes named in
`sme_thresholds.rs`, plus 256^3, 512^3 and the #87 size 2048^3. `gate_seq` is the linked
`t4a-gemm-common`'s own `wants_sme` verdict for the whole shape as one sequential call, printed by
the example. That is the kernels' gate while `Cargo.lock` holds a single `t4a-gemm-common`; the
script refuses to run otherwise, so a `t4a-gemm` bump to another range cannot leave it reading a
stale table. `matmul_calls` against the kernel hit counts says
how many sequential kernel calls each `matmul` made. A breakpoint that does not resolve to exactly
one symbol stops the script, so a renamed kernel cannot pass for "the other kernel ran".

- **1 thread: 40 of 40 runs take the route the gate predicts.** No run hit both kernels. This
  includes the edge pairs from `sme_thresholds.rs`: f64 16x64x128 goes to NEON and 32x64x64 to
  SME; f32 64x64x64 goes to NEON and 64x64x128 to SME; 256x256x32 goes to NEON for every type.
- **6 threads (held team):** every shape from 256^3 up takes SME on every member. Smaller products
  that the gate would send to SME as one call fall back to NEON (14 rows), because `gemm_tiled`
  cuts them into per-member tiles below the gate. Each of these rows shows exactly 6 kernel calls
  per `matmul` call, so the tiling branch ran, not the whole-product branch. Examples: f64
  64x64x128 (tiles under `m*n = 2048`), f32 128x128x64 (tiles under `m*n*k = 524288`), f64
  32x64x64. The rows with one kernel call per `matmul` (for example f32 16x64x128) took the
  whole-product branch.
- So "reachable wherever the gate allows" holds per sequential call, not per product on a team.
  The gate's own documentation (`sme_thresholds.rs`, end of the module comment) assumes the
  dispatcher sees "the same shape at 1 thread and at 6", and `gemm_tiled` breaks that assumption
  for these products: the thresholds were calibrated on whole products, and a tile is a smaller
  call. This is a dispatch question, the gate against the team split, and it goes to unit 3 on
  #180 together with the cost rates.

## Throughput at the #87 size, through `matmul`

2048^3, column-major, `Accum::Replace`. Each figure is the median of 11 samples (one sample is at
least 50 ms of back-to-back calls, after two untimed priming calls), with [Q1, Q3] in ms. GF/s
counts 2mnk flops for real types and 8mnk for complex types.

| f64 | 6 | 37.97 [37.16, 39.29] | 452.5 | 311.19 |
| c64 | 1 | 271.48 [271.04, 271.78] | 253.1 | 49.23 |
| c64 | 6 | 136.20 [135.66, 136.65] | 504.5 | 272.81 |

The `325e482` column is the NEON-only build before the SME fork, from the `325e482` column of
`2026-11-11-aarch64-m5-reproduction.md` (best of 4 x 3 sessions, a different harness), not a
paired A/B. An earlier run of the same shapes the same day read f64 1T at 427.4 GF/s (40.20 ms),
with the other cells within 2% (`evidence/.../timing-n2048-run1.txt`), so the f64 1T cell moves by
about 9% between runs on this unpinned host. Three observations matter for the later units of
#180:

- f64 goes from 1T to 6T by only 1.16x in this run (1.07x in the earlier run; the first review on #274 read
  1.17x). None of the runs was pinned. Contention for the
  matrix units (#180 fact 1) is the likely cause but is not established here; unit 2 measures it.
- c64 at 1T runs at 0.59x to 0.65x of the f64 rate across the two runs. The spread comes from the f64
  cell's run-to-run noise, and the runs are not the pinned acceptance protocol. #180 fact 4 expected close to 1x. c64 does scale to 6T
  (2.0x), so either the complex SME kernel or its packing is the limit at one issuer. The 5.1x gain of c64 1T over the pre-SME
  `325e482` column is not attributed here. `sme_thresholds.rs` reports c64 SME at parity with
  `neonfcma` on its grid (k <= 256), and this PR did not time `neonfcma` at 2048^3 in the same
  binary. So the gain may come from SME at large k, or from other changes to the fork since
  `325e482`. Unit 4 has to separate the two before using this cell as a rate.
- `utils::cost::Rates::AARCH64_APPLE` prices a MAC at the NEON rate: `gemm_mac` 0.037 ns (f64)
  and 0.165 ns (c64), and `gemm_single` half of each (f32, c32). Against the 1T cells above, that
  overestimates the serial time of an SME-routed 2048^3 product 7.2x (f64), 8.7x (f32), 5.2x (c64)
  and 9.7x (c32), so the width and tile gates see products several times larger than they run.

## Team/sequential bit identity on this host (found while verifying)

`cargo test -p colmat --lib` fails 5 tests on this M5 Max, on this branch and on `main` at
`318e775b` alike. CI runs the suite on Linux only, so it does not see them:

- `linalg::lu::lapack::{f32,f64}::parallel_path_is_bit_identical_to_sequential` and
  `..._with_one_column_per_member` (`lu/tests/par_identity.rs:102,123`; n = 64 width 3,
  n = 129 widths 4 and 8). These four also fail with `gemm/apple-sme` removed from the `std`
  feature, so the SME kernel does not cause them. They are an aarch64-Apple issue of their own.
- `linalg::cholesky::ldlt::factor::llt_layout_tests::llt_team_matches_sequential_bits`
  (`ldlt/factor.rs:1109`). It passes with `gemm/apple-sme` removed, so it depends on the SME
  kernel. The mechanism is not identified. The obvious candidate, the gate judging a smaller tile on
  the team (the 6-thread finding above), does not fit this test's shapes on paper. Its largest
  trailing update (about 193x193x64 at n = 257) still passes the f64 gate after a 2- to 8-way split,
  and its smaller updates fail the gate on both routes. The failing `(n, row_major, width)` case and
  the kernel counts of its updates were not recorded. Tracing them is part of unit 3, which has to
  decide how team and sequential bits stay equal on an SME host.

## Verification conclusions and constraints

The route counts and the table above are the conclusions. The example's 64-entry comparison with
a direct sum is a smoke check against gross errors only. The kernels' accuracy is covered by
`t4a-gemm`'s and colmat's own tests.

Not done here: no change to the dispatch, the gate, the cost rates or the team split. The `sme_units` budget and
the vendor-BLAS removal are later units of #180. The probe does not cover the factorizations'
trailing updates (LU, QR, Cholesky); they reach the same `matmul_imp`, but their tile shapes were
not counted.
