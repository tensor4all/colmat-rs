# Does colmat's `matmul` reach the t4a-gemm SME kernel? (2026-11-22, #180 unit 1)

Question from the review of #180: `upstream-reports/performance/perf-gemm-001-apple-sme-unused`
shows upstream `gemm` 0.19.0 never selecting a matrix-unit kernel on M4/M5. Does colmat, which
depends on the `t4a-gemm` fork, actually run the SME kernel for `f32`/`c32`/`c64` (and `f64`) at
the sizes that `t4a-gemm-common` 0.20.4 `sme_thresholds.rs` routes to SME?

## Decisions

- **Answer: yes.** The kernel is reachable for all four types. At one thread the kernel each call
  reaches is exactly the one the `sme_thresholds` gate picks, on every shape probed.
- No dispatch change is needed, so none is made. What lands is the probe (an example plus an
  lldb hit-count script), so the question can be asked again after a `t4a-gemm` bump.

## Host

Apple M5 Max, macOS 26.7.2, rustc 1.96.0, base `c82d2b8f`. `hw.optional.arm.FEAT_SME = 1`,
`FEAT_SME_F64F64 = 1`, `SME_F32F32 = 1` (this release has no `FEAT_`-prefixed spelling of the
F32F32 flag; the probe in `gemm-common/src/cache.rs` accepts both spellings), `sme_max_svl_b = 64`.
The host was shared with other work (load average 3.6 to 6.1 on 18 cores), with no pinning; macOS
has no thread affinity. Raw files are in `evidence/2026-11-22-sme-route-180/`.

## Static route

1. `faer/Cargo.toml`: the `std` feature turns on `gemm/apple-sme`, and the default features
   include `std`.
2. `linalg::matmul::matmul_imp` (`faer/src/linalg/matmul/mod.rs`), native `f32`/`f64`/`c32`/`c64`:
   - `m * n * k <= 16^3` goes to `nano_gemm`, which is far below every SME gate (the smallest is
     `m*n*k >= 131072`);
   - `Par::Team` goes to `utils::team::gemm_team`. Off x86_64 that is `gemm_tiled`, which makes one
     sequential `gemm::gemm` call per member, each on its own tile of the output;
   - otherwise one `gemm::gemm(.., Parallelism::None)` call.
3. `t4a-gemm` 0.20.1 `gemm_dispatch` calls `get_gemm_fn()` for the element type. On aarch64 Apple
   with `apple-sme`, `init_gemm_fn` returns `sme_gate::gemm_basic` when `HasAppleSme::get()`
   (f64/c64) or `::get_f32()` (f32/c32) holds. That function sends each call to `sme::gemm_basic`
   when `SmeThresholds::wants_sme(m, n, k)` holds, and to `neon`/`neonfcma` otherwise.

The gate sees the shape of each sequential call. On a team, that shape is a tile, not the whole
product.

## Dynamic route: `scripts/sme-route-probe.sh`

The script runs `faer/examples/sme_route.rs` (the public `matmul` entry, `Par::Seq` or a held
team) under lldb, and counts breakpoint hits on `<crate>::gemm::<mod>::sme::gemm_basic` and on the
NEON fallback (`neon` for f32/f64, `neonfcma` for c32/c64). It covers the crossover shapes named in
`sme_thresholds.rs`, plus 256^3, 512^3 and the #87 size 2048^3. `expected_seq` is what the gate says
for the whole shape as a single sequential call.

- **1 thread: 40 of 40 runs take the route the gate predicts.** No run hit both kernels. This
  includes the edge pairs from `sme_thresholds.rs`: f64 16x64x128 goes to NEON and 32x64x64 to
  SME; f32 64x64x64 goes to NEON and 64x64x128 to SME; 256x256x32 goes to NEON for every type.
- **6 threads (held team):** every shape from 256^3 up takes SME on every member. Smaller products
  that the gate would send to SME as one call fall back to NEON, because `gemm_tiled` cuts them
  into per-member tiles below the gate. Examples: f64 64x64x128 (tiles under `m*n = 2048`), f32
  128x128x64 (tiles under `m*n*k = 524288`), f64 32x64x64. This follows from the gate's stated
  design (it decides per sequential call). It is not a reachability bug. Whether one SME call on a
  single member beats six NEON tiles on these shapes is a question for the cost-model unit (below).

The #87 column comes from a different run, revision and harness (best of 3 to 4). It shows the
order of magnitude only and is not a paired A/B. Three observations matter for the later units of
#180:

- f64 goes from 1T to 6T for only 1.07x: six SME issuers contend for the matrix units. This fits
  #180 fact 1 (one unit per cluster).
- c64 at 1T runs at 0.59x of the f64 rate. #180 fact 4 expected close to 1x. c64 does scale to 6T
  (2.0x), so either the complex SME kernel or its packing is the limit at one issuer.
- `utils::cost::Rates::AARCH64_APPLE.gemm_mac` is 0.037 ns/MAC for f64 (about 54 GF/s, the NEON
  rate). For SME-routed shapes that overestimates the serial time about 8x, so the width and tile
  gates see a product about 8x larger than it runs.

## Team/sequential bit identity on this host (found while verifying)

`cargo test -p colmat --lib` on this branch (its library code is identical to `c82d2b8f`) fails 5
tests on this M5 Max. CI runs the suite on Linux only, so it does not see them:

- `linalg::lu::lapack::{f32,f64}::parallel_path_is_bit_identical_to_sequential` and
  `..._with_one_column_per_member` (`lu/tests/par_identity.rs:102,123`; n = 64 width 3,
  n = 129 widths 4 and 8). These four also fail with `gemm/apple-sme` removed from the `std`
  feature, so the SME kernel does not cause them. They are an aarch64-Apple issue of their own.
- `linalg::cholesky::ldlt::factor::llt_layout_tests::llt_team_matches_sequential_bits`
  (`ldlt/factor.rs:1109`). It passes with `gemm/apple-sme` removed. This is the 6-thread route
  finding above, seen as a contract failure: the sequential trailing update is one call that the
  gate sends to SME, while the team's tiles fall under the gate and run NEON, so the two
  accumulate in different orders. Keeping team and sequential bits equal on an SME host needs
  either a gate decided on the whole product (and passed to every tile), or a test that no longer
  promises the equality. That choice belongs to unit 3, not to this PR.

## Verification conclusions and constraints

The route counts and the table above are the conclusions.

Not done here: no change to the dispatch, the gate, the cost rates or the team split. The `sme_units` budget and
the vendor-BLAS removal are later units of #180. The probe does not cover the factorizations'
trailing updates (LU, QR, Cholesky); they reach the same `matmul_imp`, but their tile shapes were
not counted.
