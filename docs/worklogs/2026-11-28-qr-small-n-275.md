# f64 square QR at n = 96 and 128 against PureBLAS (colmat-rs#275)

## Decisions
- No kernel change. On this host the reported gap does not reproduce at the size the issue measured:
  colmat `qr_in_place` against `PureBLAS.geqrf!` is 1.03x at n=96 and 1.075x at n=128, one core,
  against 1.73x and 1.55x for the same kernels in the issue. The workflow for this issue is to stop
  when the ratio is absent rather than tune something that is not there.
- Stage attribution is recorded anyway for whoever reopens it: 91-93 % of the call is the
  reflector sweep of `qr_in_place_small`; building the compact-WY block factors is 5-7 % and is work
  `geqrf!` does not do. Nothing here names a stage worth changing.

## Verification conclusions and constraints
- Host is Zen 5, not the issue's znver3; only ratios are comparable. PureBLAS is master 0.1.2, not
  the Colmat.jl-pinned revision from the issue. Colmat is 1.2x slower here than on the issue's host and
  PureBLAS 2x slower, which is why the ratio moved; a znver3 re-run would be the check that matters.
- The issue's API-level numbers (`qr(A)`, `Matrix(qr(A).Q)`, 4T/8T) were not run: no Julia adapter was
  built, and the multi-thread cells are outside the single-core question.
- Instruction counts were not available (`perf_event_paranoid=4`, no valgrind).
- Raw numbers, the two probe sources and the stage table: `evidence/qr-small-n-275/results.md`.
- What would decide it: the same measurement on a znver3 host (the issue's), same harness, at the
  issue's pinned Colmat.jl revision `b376b3ce`. That separates a host effect from something that
  changed since the report. No such host was available here; if none is, the issue can be closed as
  not reproducible on available hardware. The 1.73x/1.55x to 1.03x/1.075x move is consistent with a
  host effect but is not proven to be one by this run.
- Could the unrun cells show a gap? The `qr(A)` factor cells (1.11-1.16 in the issue) are the same
  kernel plus a Julia adapter the issue says is already at native parity, so they would track the
  kernel ratio measured here. The `Matrix(qr(A).Q)` cells (1.13-1.62) are the `orgqr` path, which
  the issue itself calls a separate adapter residual (it rebuilds the block factors from `tau`), so
  they are not evidence about the factorization. The 4T/8T cells go through the blocked route's team
  products, a different code path from the one-core small path measured here, and are the only
  cells that could show a gap this run cannot see.
