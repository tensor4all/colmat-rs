# `x86-v4`: which sub-feature was wrong (colmat-rs#297)

## Decisions

- **No library change.** The defect colmat-rs#297 asked about is not in pulp, gemm or nano-gemm, and it is
  no longer in colmat: it was two bugs in colmat's own algorithms, both fixed on 2026-10-29 under
  tensor4all/faer#102 — the full-pivot LU pivot search broke ties by lane order (tensor4all/faer#105,
  `efaa5ded`), and the partial SVD's restart left a retained pair's residual estimate behind
  (tensor4all/faer#108, `1ac38c6d`). The lane count only exposed them. The `faer/Cargo.toml` comment that still
  said "non-finite factors" is corrected, and the default is not flipped here (a later step).
- **The guard is a CI lane, not a new test, and it is not in this change.** The failing cases
  already exist as tests (`test_gh238`, the `qz_real` cases,
  `test_row_major_adaptation_matches_the_column_major_one`,
  `matrix_free::svd::tests::test_small_cplx`, the two `forced_parallel` comparisons, and tensor4all/faer#105's
  `pivot_search_breaks_ties_by_column_then_row`). What is missing is that no CI job builds
  `x86-v4`, so nothing runs them with it. The lane that does is colmat-rs#298, with its exact job
  and commands; pushing a workflow change needs a token with the `workflow` scope, which the
  maintainer owns. This change carries the random-size negative control
  `faer/tests/x86_v4_probe.rs` that lane runs. Its second test prints the instruction set pulp
  dispatched to ("V4 (AVX-512)" with the feature, "V3 (AVX2)" without), which is the observability
  a default flip needs on any runner.
- **The split had to be made at run time.** `t4a-gemm-common`'s `x86-v4` is `["pulp/x86-v4"]`,
  and with one `pulp` in the lock, "gemm only" turns pulp's V4 on again through feature
  unification. That is why tensor4all/faer#86's "`gemm/x86-v4` alone fails too" did not separate anything. Nor
  can gemm-common be built without it: its AVX-512 code needs `pulp::core_arch::x86::Avx512f` and
  bytemuck's AVX-512 `Pod` impls (19 errors with the dependency removed). colmat's own SIMD loops
  dispatch through `pulp::Arch::new()`, while gemm-common and nano-gemm choose their kernels
  themselves, so the experiment used a scratch copy of pulp 0.22.2 whose `Arch::new()` skips V4
  when an environment variable is set. Each arm's dispatch was checked: base V3, pulp-only V4,
  gemm-only V3, all V4.

## Verification conclusions and constraints

Host: evo (AMD Ryzen AI 9 HX 470, Zen 5, `avx512f`), Rust 1.96.0, single-threaded test runner.

The eight tests (gh238, QZ blocked/edge/random, row-major adaptation, `test_small_cplx`,
`forced_parallel` f64/c64):

| arm | pulp dispatch | gemm / nano-gemm | `b0262938` (tensor4all/faer#86's head) | `81560db9` (`main`) |
| --- | --- | --- | --- | --- |
| no `x86-v4` | V3 | AVX2 | pass | pass |
| `pulp/x86-v4` only | V4 | AVX2 | **8 fail** | pass |
| gemm + nano-gemm AVX-512, pulp held at V3 | V3 | AVX-512 | pass | pass |
| `x86-v4` | V4 | AVX-512 | **8 fail** | pass |

- At tensor4all/faer#86's head the failures need pulp's V4 dispatch and nothing else. gemm's and nano-gemm's
  AVX-512 kernels were never involved.
- It was not test-harness contention on a many-core host: every cell above ran with
  `--test-threads=1`, and at tensor4all/faer#86's head the eight fail that way with the feature and pass that way
  without it. The 0 failures at `main` are the fixes below, not a quieter harness.
- A bisect of `b0262938..81560db9` with `--features nightly` on `test_gh238` names `efaa5ded`
  (tensor4all/faer#105). `test_small_cplx` fails 5/5 at `31f059c2` (the first parent of tensor4all/faer#108's merge) and passes
  5/5 at `1ac38c6d`. pulp is 0.22.2 at both ends.
- At `main`, the whole library and integration suite with `x86-v4` and the committed lock passes
  (63 binaries, 1157 tests), as does the negative control (300 random shapes in 1..=40, f64/c64
  products against a naive sum, full-pivot LU solves finite) in every arm.
- **A build without `x86-v4` already runs AVX-512 on the packed product.** Measured, not inferred:
  in a release build with no `x86-v4` anywhere in the feature graph, a 3000 x 3000 f64 `matmul`
  on `Par::Seq` stops (gdb) in `t4a_gemm_v0_gemm_microkernel_f64_simd512_m48_n4` under
  `private_gemm_x86::kernel_imp`. The choice is colmat's `is_x86_feature_detected!("avx512f")` in
  `linalg::matmul` and `utils::team`, not a feature. The default flip therefore widens pulp's
  loops (colmat's own SIMD code) and the `gemm`/`nano-gemm` fallbacks, not the large products.
  `perf` was not available (`perf_event_paranoid` 4), so this is a "reached", not a time share.
- **Build time**, clean test build (`cargo test -p colmat --lib --tests --no-run`, dev profile,
  `CARGO_PROFILE_DEV_DEBUG=0`, compiler cache off), two alternating runs: without `x86-v4`
  144.5 s and 137.1 s, with it 159.7 s and 162.6 s, about +15% (+20 s). This is the number for the
  opt-out recipe: the opt-out is for build time and binary size. It is not needed for old CPUs,
  because the wide functions are only entered after run-time detection. Binary size not measured.
- **Unverified:** whether GitHub's `ubuntu-latest` runner has `avx512f`. The proposed lane (#298) warns when it
  does not, and on such a runner it would guard the build and the AVX2 results only. evo is the host
  that exercised AVX-512.
- **Read, not run:** that an `x86-v4` build is safe on a host without AVX-512. pulp
  (`V4::try_new`), gemm-common (`feature_detected!("avx512f")`) and nano-gemm
  (`is_x86_feature_detected!("avx512f")`) all select the wide code at run time, but no
  AVX2-only host ran an `x86-v4` binary here.
